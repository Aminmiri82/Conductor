# Learned Rowid Index Experiment

This branch contains a proof-of-concept learned index experiment for Conductor's
bundled SQLite build. It is intentionally scoped to rowid table seeks over
`INTEGER PRIMARY KEY` data and is not a general learned secondary-index system.

## What Changed

- Conductor schema IDs were changed from text UUIDs to SQLite integer rowids.
- `src-tauri/Cargo.toml` points `rusqlite` at the local `../rusqlite` checkout.
- `rusqlite/libsqlite3-sys/build.rs` enables `SQLITE_ENABLE_LEARNED_ROWID`.
- `rusqlite/libsqlite3-sys/sqlite3/sqlite3.c` patches
  `sqlite3BtreeTableMoveto()` with a learned first probe for int-key B-tree
  pages.
- Conductor exposes SQLite experiment status, counters, enable/disable controls,
  and a microbenchmark from Settings > About > SQLite.

## Model

The SQLite patch uses a tiny page-local linear CDF model:

1. Read the first and last rowid on the current int-key B-tree page.
2. Estimate the slot for the target rowid by linearly interpolating within that
   key range.
3. Probe that estimated slot first.
4. Fall back to SQLite's existing binary-search correction inside the same page.

This is closest to a single-segment PGM-style predictor, adapted to SQLite's C
amalgamation and page-local search loop. It does not vendor SOSD's C++ PGM,
ALEX, or radix-spline code directly, because the bundled SQLite amalgamation is
compiled as C through `libsqlite3-sys`.

## Correctness Boundary

The patch only changes the first probe chosen inside a page. It does not bypass
SQLite's existing comparison loop, child-page descent, cursor positioning, or
result semantics. If the prediction is poor, SQLite still converges using the
normal binary-search correction.

The learned path is only compiled when `SQLITE_ENABLE_LEARNED_ROWID` is set. At
runtime it can be toggled with:

- `set_learned_rowid_enabled(true)`
- `set_learned_rowid_enabled(false)`

The Tauri command surface exposes the same toggle through the About settings UI.

## Counters

The patched SQLite build exports process-global counters through C APIs:

- `sqlite3_learned_rowid_reset()`
- `sqlite3_learned_rowid_enable(int enabled)`
- `sqlite3_learned_rowid_enabled()`
- `sqlite3_learned_rowid_stats(...)`

Conductor surfaces these as:

- table moveto calls
- learned attempts
- fallbacks
- exact first probes
- B-tree rowid comparisons

## Benchmark

The benchmark command creates a temporary table:

```sql
CREATE TEMP TABLE learned_rowid_probe(
  id INTEGER PRIMARY KEY,
  payload TEXT NOT NULL
);
```

It runs two deterministic scenarios:

- `dense`: 5,000 rowids from `1..=5000`
- `sparse quadratic`: 5,000 monotonic rowids generated by `id * id * 3 + id * 11`

Each scenario runs 4,096 deterministic point lookups twice:

1. learned rowid disabled
2. learned rowid enabled

It reports comparison counts, comparisons per lookup, elapsed microseconds, and
the comparison delta for each scenario. The sparse scenario is included so the
experiment makes distribution sensitivity visible instead of only demonstrating
the best-case dense integer pattern.

Run it from the app:

1. Open Settings.
2. Go to About.
3. Use the SQLite experiment controls.
4. Click Benchmark.

The focused Rust tests assert that:

- learned counters increment for integer rowid lookups
- learned mode can be disabled for comparison
- the benchmark path compares enabled and disabled runs
- the dense integer-rowid fixture performs fewer B-tree comparisons with the
  learned first probe enabled

## Limitations

- This is not a persistent learned-index catalog.
- It does not change SQLite's query planner.
- It does not replace secondary indexes.
- It does not materialize model data on disk.
- It does not use SOSD C++ implementations directly.
- It is expected to help dense or near-linear rowid distributions more than
  sparse or irregular rowid distributions.

The experiment is useful because Conductor now has integer rowid IDs and common
ID lookups travel through this modified SQLite B-tree seek path.
