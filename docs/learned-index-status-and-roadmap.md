# Learned Index Status and Roadmap

## Short Version

It is possible to modify the local `rusqlite`/SQLite stack and add a
planner-visible native SQLite learned-index path.

The current patch is now a minimal native SQLite learned-index path for rowid
equality lookups, but it is not yet a full SQLite `Index` subtype with
independent planner costing.

What we now have is a model-backed SQLite-engine experiment for integer-rowid
B-tree seeks. Conductor builds a static PGM-style segment model over sorted
rowids, persists the model metadata in the app database, registers the model
with patched SQLite by table root page, and then SQLite uses that model to pick
the first slot probe inside `sqlite3BtreeTableMoveto()`.

SQLite's normal B-tree correction still finishes the seek, so correctness still
comes from SQLite's existing table lookup path.

We implemented a small PGM-style model builder.

We now implement a minimal `CREATE LEARNED INDEX` path for rowid-equivalent
integer primary keys:

```sql
CREATE LEARNED INDEX idx_requests_id_pgm ON requests(id);
```

The minimal native path builds a C-side PGM-style model inside the bundled
SQLite build, persists it in `learned_index_models`, registers it with the
SQLite learned-rowid registry, and annotates `EXPLAIN QUERY PLAN` for supported
rowid equality plans as `USING LEARNED INTEGER PRIMARY KEY`.

This is planner-visible for the rowid equality path, but it still reuses
SQLite's normal rowid seek plan and the existing B-tree correction fallback.

We did not use SOSD's PGM implementation.

We did not use SOSD's ALEX implementation.

We did not use SOSD's radix spline implementation.

## What We Actually Changed

### Conductor Schema

Conductor's database schema now uses integer IDs instead of text UUIDs for the
core app entities:

- `collections.id`
- `requests.id`
- `collection_nodes.id`
- `environments.id`
- `request_history.id`

Foreign-key columns were updated to integer IDs as well. This matters because
SQLite rowid tables are the easiest place to experiment with learned lookup
behavior.

### Rust and TypeScript ID Plumbing

The app now treats entity IDs as numeric IDs through the Rust command layer and
frontend TypeScript types.

Rust inserts generally omit explicit IDs and use SQLite's generated rowid via
`last_insert_rowid()`.

Frontend ID types now use `number` instead of string UUIDs, with explicit string
conversion only at UI boundaries like select/drop values.

### Local rusqlite

`src-tauri/Cargo.toml` now points to the local `../rusqlite` checkout.

`rusqlite/libsqlite3-sys/build.rs` enables:

```c
SQLITE_ENABLE_LEARNED_ROWID
```

That makes the bundled SQLite build compile the experiment code.

### SQLite Engine Patch

The actual engine patch is in:

```text
rusqlite/libsqlite3-sys/sqlite3/sqlite3.c
```

It modifies:

```c
sqlite3BtreeTableMoveto()
```

That function is part of SQLite's B-tree layer for seeking into rowid tables.

The patch adds:

- runtime enable/disable state
- process-global counters
- exported C APIs for reading/resetting counters
- exported C APIs for registering and clearing learned rowid models
- a root-page keyed in-memory model registry
- model-backed first-slot prediction for rowid table seeks

The current model-backed predictor:

1. Finds the learned rowid model registered for the cursor's table root page.
2. Uses the model segment for the target rowid to predict an approximate global
   row position.
3. Maps that global prediction back onto the current B-tree page's slot range.
4. Uses that predicted slot as the first probe.
5. Falls back to SQLite's existing binary-search correction.

So correctness still comes from SQLite's normal B-tree search logic. The learned
piece only chooses a better or worse first guess.

### PGM-Style Model and Metadata

Conductor now builds a compact static PGM-style segment model in Rust for rowid
tables. It currently targets:

- `requests(id)`
- `collection_nodes(id)`
- `request_history(id)`

The model metadata is persisted in:

```sql
learned_index_models
```

The model can be rebuilt manually from Settings > About > SQLite. Persisted
models are reloaded on database open and registered with SQLite's in-memory
model registry.

### App Controls and Benchmark

Conductor now exposes the experiment in Settings > About > SQLite:

- enable learned rowid seek
- disable learned rowid seek
- reset counters
- rebuild models
- run benchmark

The benchmark currently runs two deterministic scenarios:

- `dense`: rowids `1..=5000`
- `sparse quadratic`: rowids generated by `id * id * 3 + id * 11`

For each scenario, it runs the same lookups twice:

1. learned disabled
2. learned enabled

It reports:

- row count
- lookup count
- disabled comparisons
- enabled comparisons
- comparisons per lookup
- comparison delta
- elapsed microseconds
- exact first probes
- learned attempts
- model count
- segment count
- model memory
- model predictions
- average prediction error
- max prediction error

## What This Is

This is a real model-backed SQLite-engine experiment.

It lives below rusqlite, inside SQLite's B-tree seek path.

It runs when Conductor performs rowid-table lookups over `INTEGER PRIMARY KEY`
tables.

It is useful for answering:

- Do our integer IDs go through a path where a learned predictor can affect
search behavior?
- Can we patch bundled SQLite through local `rusqlite` and expose experiment
controls to the app?
- Can we compare learned vs normal B-tree behavior from inside Conductor?
- Does a PGM-style model reduce comparisons on dense or near-linear rowid data?

## What This Is Not

This now has a minimal native SQLite learned-index DDL path for
`INTEGER PRIMARY KEY` rowid aliases.

It is visible in `EXPLAIN QUERY PLAN` for supported rowid equality searches.

It is not ALEX.

It is not radix spline.

It does not replace SQLite secondary indexes like:

```sql
CREATE INDEX idx_requests_collection ON requests(collection_id);
```

It does not support arbitrary indexed columns.

It does not support text keys.

It does not create a new SQLite index type.

It supports syntax like:

```sql
CREATE LEARNED INDEX ...
```

for one shape only: `CREATE LEARNED INDEX name ON table(integer_primary_key)`.

## Did We Use SOSD?

Only for evaluation and direction.

SOSD contains relevant implementations:

- `SOSD/competitors/pgm_index.h`
- `SOSD/competitors/alex.h`
- `SOSD/competitors/rs.h`
- `SOSD/competitors/radix_binary_search.h`

But those are C++benchmark-oriented implementations. The bundled SQLite
amalgamation used by `libsqlite3-sys` is compiled as C. Directly dropping SOSD's
C++ headers into `sqlite3.c` would force a much more invasive build and ABI
change.

So the current patch uses the PGM-style idea of approximating key position, but
it does not reuse SOSD code.

## Can We Add an Honest Learned Index?

Yes.

There are three realistic levels.

## Option 1: Sidecar Learned Index in Conductor

This is the implemented prototype path.

SQLite remains mostly unchanged. Conductor owns a learned-index sidecar for
specific tables/columns.

Example:

- Build a PGM model over `requests.id`.
- Store model metadata in a normal SQLite table or app-side file.
- On lookup, Conductor calls the learned model first to get a predicted rowid
range.
- Then Conductor queries SQLite with a bounded rowid range or direct rowid
lookup.

This can be honest PGM without making SQLite understand a new index type.

Pros:

- Much easier than changing SQLite planner internals.
- Can use a Rust PGM implementation or a small C/Rust implementation we write.
- Easy to benchmark inside Conductor.
- Low risk to SQLite correctness.

Cons:

- SQLite's query planner does not know about it.
- Only code paths we manually route through the learned index benefit.
- It is more of an application-level learned index than a SQLite index.

Implemented initial targets:

```text
requests(id)
collection_nodes(id)
request_history(id)
```

Status: implemented for rowid-table first-probe acceleration, with manual
rebuild and SQLite B-tree verification fallback.

## Option 2: SQLite Virtual Table or Extension

Implement a learned-index-backed virtual table or eponymous table-valued
function.

Example shape:

```sql
SELECT rowid_lo, rowid_hi
FROM learned_predict('requests', 'id', ?);
```

Then queries can use that prediction to constrain SQLite work.

Pros:

- Lives closer to SQLite.
- Can be exposed through SQL.
- Does not require rewriting core SQLite planner/index internals.

Cons:

- Still not a native SQLite index.
- Query plans need manual query rewriting or app cooperation.
- More awkward than direct app-side Rust if only Conductor uses it.

Estimated difficulty: moderate to high.

## Option 3: Native SQLite Learned Index Type

This is the "honest to god SQLite learned index" path.

It means teaching SQLite that a learned index is a real schema object, probably
with syntax or metadata similar to:

```sql
CREATE LEARNED INDEX idx_requests_id_pgm ON requests(id);
```

To do that properly, we would need to modify several SQLite subsystems.

Likely areas:

- parser grammar for new syntax, or overloaded `CREATE INDEX`
- schema storage in `sqlite_schema`
- `Index` metadata structures
- model build/rebuild code
- model persistence format
- write-path maintenance on insert/update/delete
- planner costing in `where.c`
- VDBE opcodes or helper paths for learned seeks
- fallback verification against the table B-tree
- integrity/check tooling

The model itself could be:

- PGM-style piecewise linear segments
- radix spline
- RMI
- eventually ALEX, though ALEX is more dynamic and more complex

For SQLite, PGM or radix spline are better first choices than ALEX because they
are compact, static-ish, and easier to serialize.

Pros:

- Real SQLite index type.
- Planner-visible.
- Could support normal SQL queries without app-specific routing.

Cons:

- Large invasive patch.
- Harder to keep correct across SQLite updates.
- Needs model persistence and maintenance semantics.
- Much more testing required.

Estimated difficulty: high.

## Current Next Step

Phase D initial is implemented: learned indexes are planner-visible for the
supported rowid equality path.

Phases A, B, C, and the first Phase D slice are implemented:

1. PGM-style segment builder over sorted `i64` rowids.
2. Model-backed benchmark fixtures.
3. Root-page keyed SQLite model registry.
4. Model-based first-slot prediction in `sqlite3BtreeTableMoveto()`.
5. SQLite B-tree correction as the correctness fallback.
6. Counters for model segments, model memory, model predictions, prediction
   error, and comparisons.
7. Persistent Conductor-owned model metadata.
8. Minimal `CREATE LEARNED INDEX ... ON table(id)` support.
9. `EXPLAIN QUERY PLAN` annotation for learned-backed rowid equality seeks.

That gets us from a page-local learned-ish probe to an actual learned model.
What remains is not "can we build a model?" anymore. We can. The remaining
question is how far to push native SQLite integration beyond the rowid path:
source-level grammar, a real `Index` subtype, independent costing, and write
maintenance.

## Practical Implementation Plan

### Phase A: Real PGM Model, Still Experimental - Implemented

Implemented result:

- actual PGM-like learned model
- Rust segment builder over sorted `i64` rowid keys
- benchmark fixture model builds for dense and sparse rowid distributions
- model lookup returning approximate global row position
- still no SQLite planner integration
- still correctness-safe through B-tree verification

### Phase B: Per-Table Learned Model Registry - Implemented

The patched SQLite layer now has a small registry keyed by SQLite root page.

Example:

```text
root_page -> learned_rowid_model
```

Then `sqlite3BtreeTableMoveto()` can use a table-specific model instead of a
page-local interpolation.

This is the point where the experiment becomes much more real for Conductor's
tables.

Prototype limits:

- models are process-memory copies after registration
- rebuild is manual from the app
- writes do not incrementally maintain the model yet
- stale models are not automatically detected or maintained yet

For the prototype, rebuilding manually from the app is acceptable. The initial
Phase D path makes registered models visible for supported rowid equality plans.

### Phase C: Persistent Model Metadata - Implemented

Model segments are stored durably in a Conductor-owned metadata table.

Chosen option:

- a Conductor-owned metadata table

Deferred options:

- hidden normal SQLite tables
- custom SQLite extension storage
- embedded in SQLite index pages, if going fully native

Current shape:

```sql
CREATE TABLE learned_index_models (
  table_name TEXT NOT NULL,
  column_name TEXT NOT NULL,
  root_page INTEGER NOT NULL,
  model_json TEXT NOT NULL,
  row_count INTEGER NOT NULL,
  max_error INTEGER NOT NULL,
  built_at TEXT NOT NULL,
  PRIMARY KEY (table_name, column_name)
);
```

This is not as pure as native SQLite index pages, but it is easy to inspect and
iterate on.

Implemented prototype status:

- A greedy static PGM-style segment builder now builds models over sorted `i64`
  rowid keys in Rust.
- The patched SQLite amalgamation has a process-memory learned rowid model
  registry keyed by table root page.
- `sqlite3BtreeTableMoveto()` uses a registered model to choose the first probe
  inside int-key B-tree pages, then keeps SQLite's normal correction path as the
  correctness fallback.
- Conductor persists models in `learned_index_models` and reloads them on
  database open.
- Settings > About > SQLite can rebuild persisted models and shows model count,
  segment count, model memory, prediction count, and slot-error stats.
- The learned-rowid benchmark builds model-backed dense and sparse fixtures and
  reports model memory plus prediction-error counters.

### Phase D: Planner-Visible Native Index - Initial Implementation

The first Phase D implementation is now in place for the smallest useful native
SQLite target.

This is the serious research-engineering phase.

It likely means working from `sqlite-src-learned-experiment/src/*.c` rather than
only the amalgamated `sqlite3.c`, then regenerating the amalgamation or porting
the patch back into `rusqlite/libsqlite3-sys/sqlite3/sqlite3.c`.

Goal:

```sql
CREATE LEARNED INDEX idx_requests_id_pgm ON requests(id);
```

Implemented behavior:

- `CREATE LEARNED INDEX name ON table(id)` is accepted by the bundled SQLite
  prepare path.
- The supported column must be an `INTEGER PRIMARY KEY` rowid alias.
- SQLite builds the PGM-style model in C from sorted rowids.
- SQLite persists the model payload in `learned_index_models` with a durable
  `index_name`.
- Persisted models reload without the previous Conductor-only table whitelist.
- `EXPLAIN QUERY PLAN` annotates supported rowid searches as
  `USING LEARNED INTEGER PRIMARY KEY`.
- VDBE execution uses the existing model-backed rowid seek path in
  `sqlite3BtreeTableMoveto()`.
- Table B-tree verification remains the correctness fallback.

Still deferred:

- parser-generator-level grammar support in SQLite source form
- a separate `Index` subtype in SQLite schema memory
- independent learned-index planner costing
- write-path model maintenance or automatic stale marking
- range predicates
- non-rowid columns
- compound learned indexes
- text keys
- `DROP LEARNED INDEX` / rebuild syntax

Minimal native target status:

- support `INTEGER PRIMARY KEY` / rowid-equivalent single-column learned indexes:
  implemented
- support equality lookups first: implemented through the rowid equality path
- keep range predicates for a later pass: still deferred
- reject unsupported columns and compound indexes clearly: implemented
- store model payload in ordinary metadata at first, even if the schema object is
  planner-visible: implemented

Required SQLite work areas:

- parser support or a compatible syntax strategy
- `sqlite_schema` representation
- `Index`/schema metadata additions
- model build and rebuild path
- model serialization format
- staleness semantics after insert/update/delete
- planner costing in `where.c`
- execution path changes in VDBE/B-tree glue
- integrity checks and fallback verification tests

Recommendation:

Before expanding past the current Phase D slice, collect benchmark output from
realistic Conductor data. If the model does not produce a clear
lookup/comparison win there, adding a deeper `Index` subtype and planner costing
will add complexity without proving value.

## Which Learned Index Should We Pick?

For this project:

1. PGM first.
2. Radix spline second.
3. ALEX later, if we want dynamic update behavior.

PGM is the best first real target because:

- compact model
- simple lookup contract
- easy to serialize
- natural fallback window
- good fit for sorted integer keys
- much easier than ALEX inside SQLite

Radix spline is also reasonable, but PGM is conceptually cleaner for a thesis-y
learned-index prototype.

ALEX is interesting, but it is a bigger data structure with more moving parts.
It makes more sense after we prove the simpler static model path.

## Recommended Immediate Work

If we continue from here, the next concrete task should be one of these:

1. Benchmark the implemented learned-index path on real imported Postman
   collections and request-history data.
2. Tighten model maintenance semantics: stale markers, row-count checks, and
   automatic rebuild prompts.
3. Expand Phase D beyond the rowid equality path with source-level grammar,
   planner costing, range predicates, and eventually non-rowid keys.

Phase D first deliverables:

- syntax decision and schema representation: implemented with
  `CREATE LEARNED INDEX` and `learned_index_models.index_name`
- one supported shape: `CREATE LEARNED INDEX ... ON table(id)`: implemented
- persisted model metadata connected to the schema object: implemented through
  the learned-index catalog row
- planner path for `WHERE id = ?`: implemented as a learned-backed rowid plan
  visible in `EXPLAIN QUERY PLAN`
- execution path that uses learned prediction plus B-tree verification:
  implemented
- tests proving exact-hit, missing-key, stale-model, rebuild, and fallback
  behavior: partially implemented; exact-hit, persistence reload, unsupported
  column rejection, enabled/disabled fallback, and benchmark paths are covered

That would be the first version I would call a native SQLite learned index.
